# Архитектура

## Общий подход

Проект строится как небольшой модульный монолит. FastAPI обслуживает отдельные
API-маршруты и встроенный минимальный server-rendered frontend.
SQLAlchemy работает синхронно: для текущего масштаба это проще и не добавляет
лишнюю сложность. PostgreSQL является постоянным хранилищем, Alembic управляет
изменениями схемы.

`app/main.py` только собирает приложение и подключает routers. Конфигурация из
окружения находится в `app/config.py`, а engine, общий `DeclarativeBase` и
фабрика сессий — в `app/database.py`.

## Зоны ответственности

- `routers/` — HTTP-контракты: разбор запроса, зависимости, коды ответа и вызов
  сервисов. Сложная логика и большие SQL-запросы сюда не помещаются.
- `services/` — прикладные сценарии и правила доступа. Сервисы будут принимать
  SQLAlchemy `Session` и работать непосредственно с ORM-моделями; отдельный
  repository layer для этого проекта не нужен.
- `models/` — только SQLAlchemy ORM-модели и связи между ними.
- `schemas/` — только Pydantic-модели входных и выходных API-данных.
- `templates/` и `static/` — минимальный HTML/CSS/JavaScript frontend.

Модули предметной области будут добавляться по мере реализации сценариев, а не
заранее в виде пустых классов и функций.

## Модель пользователя

Сущность `User` хранится в таблице `users`. Поле `username` уникально и будет
идентификатором для авторизации. Перед использованием username
нормализуется через `strip().casefold()` и проверяется по единому набору правил.
В базе нет поля с исходным паролем: `password_hash` содержит результат
хеширования Argon2, а исходный пароль существует только во время обработки
запроса.

Роль ограничена значениями `user` и `admin` одновременно Python enum и
именованным PostgreSQL enum `user_role`. Новому пользователю по умолчанию
назначается роль `user`; публичная регистрация не принимает роль от клиента.

Публичный `POST /api/auth/register` принимает только username и пароль.
Неожиданные поля отклоняются, а роль и активность задаются backend: публичная
регистрация всегда создаёт активного пользователя с ролью `user`. Предварительная
проверка дубликата даёт понятный ответ, а `UNIQUE` constraint и обработка
`IntegrityError` сохраняют гарантию при конкурентных запросах.

Первый администратор не создаётся автоматически и не имеет предустановленных
учётных данных. Оператор явно запускает management command
`python -m app.scripts.create_admin`, которая применяет те же правила username и
пароля, нормализацию и Argon2-хеширование, но назначает `UserRole.ADMIN`.
Существующая учётная запись этой командой не повышается. После bootstrap
дальнейшее управление ролями выполняется через защищённый admin API.

## Authentication

`POST /api/auth/login` проверяет нормализованный username, Argon2 hash и
активность пользователя. При успехе создаётся короткоживущий JWT access token с
claims `sub`, `iat` и `exp`. Token хранится только в cookie с `HttpOnly`,
`SameSite=Lax` и `Path=/`; флаг `Secure` включается настройкой окружения. В JSON
token не возвращается.

Для неизвестного username выполняется одна проверка Argon2 относительно
заранее созданного dummy hash. Он создаётся один раз при загрузке процесса и не
используется для реальных учётных записей. Это убирает явную timing-разницу
между отсутствующим пользователем и неверным паролем существующего пользователя.

Dependency `get_current_user` читает cookie, проверяет подпись и срок JWT, после
чего загружает пользователя из БД. Существование, активность и роль всегда
берутся из актуальной записи, а не считаются доверенными claims token. Endpoint
`GET /api/auth/me` возвращает безопасное представление текущего пользователя.
`POST /api/auth/logout` удаляет cookie; серверного blacklist нет, поэтому уже
скопированный token остаётся действительным до `exp`.

Изменение роли и деактивация поэтому действуют на уже выпущенный JWT со
следующего запроса. После повторной активации тот же token снова принимается,
если его `exp` ещё не наступил: blacklist и принудительный отзыв token в текущей
stateless-схеме отсутствуют.

## CSRF-защита

`SameSite=Lax` уменьшает риск части cross-site запросов, но HttpOnly cookie не
решает CSRF полностью. Поэтому приложение использует double-submit token:
публичный `GET /api/auth/csrf` генерирует криптографически случайное значение,
возвращает его в JSON и записывает в cookie `csrf_token`. Эта cookie намеренно
не имеет `HttpOnly`, чтобы same-origin JavaScript frontend мог передать
значение в заголовке `X-CSRF-Token`.

Для изменяющих запросов backend требует одновременно cookie и header и
сравнивает их constant-time функцией. Защищены registration, login, logout,
создание/изменение/удаление заметок и изменение пользователя администратором.
GET-запросы CSRF token не требуют. После logout удаляются access-token и CSRF
cookie; повторный вызов `/api/auth/csrf` выдаёт новое значение.

Предполагается same-origin frontend внутри FastAPI. CORS middleware, в том
числе permissive CORS с credentials, не добавлен. CSRF является дополнительной
проверкой и не заменяет authentication, ownership или `require_admin`.
Refresh tokens отсутствуют.

## Модель заметок и доступ

Связь предметных сущностей — `User 1 -> N Note`. Таблица `notes` хранит
обязательный `owner_id` с внешним ключом на `users.id`; для выборки заметок
пользователя на нём есть индекс. Поле `owner_id` отсутствует во входных и
публичных выходных API-схемах: при создании backend берёт его только из
аутентифицированного пользователя.

Для чтения, изменения и удаления конкретной заметки запрос всегда
одновременно ограничивается идентификатором заметки и владельцем:
`note.id == requested_note_id AND note.owner_id == current_user.id`. Проверка
выполняется backend-слоем независимо от интерфейса. Такой запрос не раскрывает
чужую заметку. Чужая и несуществующая заметки имеют одинаковый публичный ответ
`404 Note not found`. Список также фильтруется по `owner_id` непосредственно в
БД, а не в Python.

CRUD доступен под `/api/notes`: создание, список, чтение, PATCH и удаление.
Обычные маршруты всегда являются личными, поэтому пользователь с ролью `admin`
там тоже видит только собственные заметки и не получает обход ownership.

## Административный доступ

Dependency `require_admin` надстраивается над `get_current_user` и проверяет
актуальную ORM-роль `UserRole.ADMIN`, загруженную из БД. Роль из JWT не
используется. Анонимный запрос получает `401`, а активный пользователь без
admin-роли — `403`.

Маршруты `/api/admin/*` отделены от personal API. Администратор может читать
список пользователей и отдельного пользователя, а также изменять только
`role` и `is_active`. Самопонижение и самодеактивация отклоняются с `409`, чтобы
администратор не заблокировал собственную текущую учётную запись. Проверка того,
что в системе всегда остаётся хотя бы один доступный admin, пока отсутствует:
другой администратор может понизить или деактивировать последнего доступного
администратора.

Через `/api/admin/notes` администратор может только читать все заметки и видеть
их `owner_id`. Создание, изменение и удаление заметок в admin API отсутствуют.
Для собственных операций любой роли, включая admin, используется исключительно
owner-scoped `/api/notes`.

## Frontend

Frontend встроен в FastAPI и доступен через отдельный page router. Jinja2
формирует только HTML shell для `/login`, `/register`, `/notes` и `/admin`, а
vanilla JavaScript работает с уже существующим JSON API через same-origin
Fetch. SQLAlchemy-запросов и бизнес-логики в page routes нет; Node.js и
отдельный frontend server не используются.

Access JWT остаётся в HttpOnly cookie и никогда не читается JavaScript. Общий
API helper получает CSRF token через `/api/auth/csrf` и добавляет его в
`X-CSRF-Token` только для unsafe методов. Токен хранится только в памяти
страницы. Пользовательский текст заметок и username добавляются в DOM через
`textContent`/`value`, без HTML rendering и Markdown.

Проверки роли и состояния авторизации во frontend используются только для UX:
скрытия admin-ссылки и redirect между страницами. Конечной границей безопасности
остаются `get_current_user`, ownership-фильтры и `require_admin` backend.

Если первый logout-запрос получает CSRF `403`, frontend один раз сбрасывает
локально закэшированный CSRF token, получает новый и повторяет logout. При
сетевой или повторной ошибке redirect на `/login` не выполняется: интерфейс
сообщает, что сессия остаётся активной, и позволяет повторить действие.

## Security hardening

Конфигурация отклоняет известные публичные JWT placeholders. Пример окружения
содержит намеренно невалидное `CHANGE_ME`, поэтому без явного случайного секрета
приложение завершается при загрузке Settings. В production-конфигурации
`COOKIE_SECURE=true` обязателен; development по HTTP допускает `false`.

SQLAlchemy engine использует `hide_parameters=True`, чтобы bound parameters —
включая содержимое заметок и password hashes — не включались в представление
ошибок. Схемы заметок отдельно отклоняют NUL с `422`, поскольку PostgreSQL text
его не поддерживает. Идентификаторы path ограничены диапазоном PostgreSQL
INTEGER, а формат и длина CSRF token проверяются до constant-time сравнения.

Централизованный middleware добавляет CSP с `frame-ancestors 'none'`,
`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` и
`Referrer-Policy: no-referrer`. API и HTML-страницы получают
`Cache-Control: no-store`. HSTS не выставляется приложением в локальном HTTP;
его следует включать на HTTPS ingress. Для встроенной документации FastAPI
действует отдельная CSP, допускающая только необходимые ресурсы jsDelivr.

## Границы текущего этапа

Сейчас существуют конфигурация, SQLAlchemy-инфраструктура, модели `User` и
`Note`, их миграции и схемы, Argon2-хеширование, публичная регистрация,
login/logout, JWT access token в HttpOnly cookie, получение текущего
пользователя, owner-scoped CRUD заметок, Docker-окружение и `/health`.
Также реализованы role-based admin authorization, просмотр пользователей,
изменение их роли/активности, read-only просмотр всех заметок и double-submit
CSRF-защита изменяющих API-запросов, а также минимальный Jinja2/vanilla JS
frontend. Намеренно не реализованы refresh tokens, token blacklist, server-side
CSRF sessions, удаление пользователей, изменение их username/password через
admin API, admin-запись заметок, SPA framework, поиск, pagination и расширенные
функции заметок.
